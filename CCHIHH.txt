\begin{abstract}
Cloud--edge--device (CED) collaborative scheduling in distributed manufacturing requires three coupled decisions: offloading each computational task to a cloud or edge server, sequencing manufacturing operations across devices, and assigning each operation to a specific device. These three decision types have fundamentally different search characteristics, yet existing methods optimize them with a single set of operators, which mixes improvement signals and becomes unreliable as the number of tasks grows. This paper proposes CCHIHH, a hyper-heuristic algorithm that decomposes the CED scheduling problem into three blocks via cooperative coevolution, and introduces three mechanisms to improve search quality at scale: (i)~a linear contextual bandit that selects operators independently within each block based on the current search state, (ii)~heterogeneous islands with ring migration that maintain multiple complementary search strategies in parallel, and (iii)~a stability-gating mechanism that delays diversity injection until stagnation is detected, protecting convergence on large instances. Experiments on instances with up to 500 tasks and 800 devices show that CCHIHH improves the weighted objective by 33.59\% over CGA, 43.99\% over IMOMA, 30.04\% over DSAC-DE, and 54.72\% over PPO on the largest instance ($p < 0.05$), while keeping the coefficient of variation below 0.051 across all scales.
\end{abstract}

\section{Introduction}
\label{sec1}
%% Labels are used to cross-reference an item using \ref command.

Industrial Internet-of-Things (IIoT) platforms connect cloud data centers, edge servers, and local manufacturing devices to support distributed production. In such platforms, two categories of workloads coexist. \emph{Cloud--Edge (CE) tasks} are computation-intensive or latency-sensitive applications---such as digital twin simulation, quality prediction, and machining control---that must be offloaded to either a cloud server (high capacity, high latency) or a nearby edge server (moderate capacity, low latency). \emph{Manufacturing (M) tasks} consist of jobs, each containing a sequence of operations (e.g., welding, painting, assembly) executed on local industrial devices. The two categories are coupled through synchronization constraints: for example, a digital twin simulation task cannot start until the associated machining operation begins collecting sensor data, and an assembly quality prediction task cannot finish until all related subassembly operations are completed.

These couplings create a joint scheduling problem with three interdependent decision types:
\begin{enumerate}
    \item \textbf{CE offloading}: assigning each CE task to a cloud or edge server based on its computation demand and latency requirement;
    \item \textbf{Operation sequencing}: determining the global execution order of manufacturing operations from different jobs on shared devices;
    \item \textbf{Device assignment}: selecting a specific local device for each manufacturing operation from its eligible device set.
\end{enumerate}

The three decisions are tightly coupled. The offloading decision affects communication latency and energy consumption, which in turn affect the synchronization timing with manufacturing operations. The sequencing decision determines which operations compete for the same device, influencing the device assignment quality. Together, the combined solution space has complexity $\mathcal{O}(2^{N_{CE}} \times (N_c + N_e)^{N_{CE}} \times \prod_{j}(n_j!) \times N_d^{N_{\mathrm{ops}}})$, where $N_{CE}$ is the number of CE tasks, $N_{\mathrm{ops}} = \sum_j n_j$ is the total number of manufacturing operations, and $N_c$, $N_e$, $N_d$ are the numbers of cloud servers, edge servers, and devices, respectively.

Existing methods for CED scheduling exhibit three recurrent limitations as problem scale grows. \emph{First}, most methods treat the entire decision vector as one block and apply operators globally. When a single operator improves offloading but simultaneously degrades device assignment, the mixed feedback signal makes it difficult to learn which operator is truly effective for which decision type~\cite{sun2020adaptive,de2021comparative}. \emph{Second}, single-population methods maintain only one search trajectory. As the landscape becomes more complex at large scale, they tend to converge prematurely~\cite{gong2011distributed,whitley1999island}. \emph{Third}, methods that inject diversity through random restart or immigration~\cite{wang2020task} risk disrupting promising solutions during late-stage convergence, reducing reliability.

To address these limitations, this paper proposes CCHIHH (Cooperative Coevolution Hyper-Heuristic with Heterogeneous Islands). The algorithm first decomposes the CED scheduling problem into three blocks (offloading, sequencing, and device assignment) using cooperative coevolution, and then applies three mechanisms that form the main contributions of this paper:
\begin{enumerate}
    \item \textbf{Localized contextual bandit}: A linear contextual bandit is maintained independently for each block on each island. It observes a seven-dimensional search state (including generation progress, stagnation level, diversity, and recent improvement) and selects the most suitable operator for that specific block. This avoids the reward-mixing problem of global operator selection.
    
    \item \textbf{Heterogeneous islands with ring migration}: The population is partitioned into multiple islands, each evolving independently with its own bandit and operator weights. A ring migration topology periodically transfers the best individual from each island to its neighbor, enabling information sharing without homogenizing the search.
    
    \item \textbf{Stability-gated diversity control}: A gating mechanism monitors stagnation on each island and blocks the diversity-injection operator (Block Resample) until stagnation exceeds a threshold. This protects convergence during productive phases while allowing escape from local optima when progress stalls. The benefit is most pronounced on large-scale instances.
\end{enumerate}

Experiments on three problem scales (100, 200, and 500 tasks) demonstrate that CCHIHH achieves significant improvements over representative baselines, with the performance gap widening as instance scale increases. Ablation studies confirm that each component becomes increasingly important at larger scales, suggesting that the algorithm's overhead is justified precisely when the scheduling problem is most complex.

The remainder of this paper is organized as follows. Section~\ref{sec2} reviews related work. Section~\ref{sec3} formulates the CED collaborative scheduling problem. Section~\ref{sec4} presents the proposed CCHIHH algorithm. Section~\ref{sec5} reports experimental results. Section~\ref{sec6} concludes the paper.

\section{Related Works}
\label{sec2}

This section reviews existing research on CED collaborative task scheduling from two aspects: problem modeling and algorithm design.

\subsection{Task Scheduling Models in CED Collaboration}
\label{subsec21}

\textbf{Architecture and tier modeling.}
Early research focuses on single-tier scheduling (cloud-only or edge-only), reducing the problem to a two-dimensional decision space~\cite{avan2023state,latip2024metaheuristic}. Recent studies extend to three-tier architectures. Laili et al.~\cite{laili2021parallel} establish a CED model with two collaboration modes. Zhang et al.~\cite{zhang2022deadline} propose a deadline-aware method for cloud--edge computation but do not address cross-tier manufacturing integration. Liu et al.~\cite{liu2023joint} jointly optimize offloading decisions focusing on latency reduction. Li et al.~\cite{li2024energy} use directed acyclic graphs (DAGs) for energy-limited task scheduling across three tiers. However, DAG-based approaches primarily target computational tasks and neglect the job-shop characteristics of device-tier operations.

\textbf{Dependency modeling and constraint handling.}
Task dependencies are typically represented by DAGs~\cite{li2024energy,zhang2022adaptive,li2024dynamic}, where vertices denote tasks and edges denote precedence. Resource capacity constraints (CPU and memory limits~\cite{liu2025energy,liu2025resource,chen2022task}), device eligibility constraints~\cite{yin2024cloud,chen2022task}, and deadline constraints~\cite{avan2023state,zhang2022deadline} are investigated separately. However, existing models rarely integrate these constraints simultaneously for multi-operation CED scheduling with cross-tier synchronization dependencies.

\textbf{Objective formulation.}
Common objectives include minimizing makespan~\cite{avan2023state,li2024energy} and energy consumption~\cite{liu2025energy,liu2025resource}. Bi-objective formulations combining both are emerging~\cite{laili2021parallel,cui2025efficient,li2024dynamic,zhang2025reinforcement}, typically using weighted-sum aggregation. Few studies investigate the trade-offs between cloud-tier efficiency, edge-tier latency, and device-tier energy sustainability in an integrated manner.

\textbf{Problem scale.}
Most studies analyze small instances (10--100 tasks) and formulate the solution space as $O(k^n)$, treating all resources as homogeneous. Recent work~\cite{li2024energy,cui2025efficient} acknowledges that combined offloading--sequencing--assignment decisions produce larger solution spaces, but these studies do not exploit the decomposability of the decision space. Industry-scale instances (hundreds of tasks and devices) remain underexplored~\cite{yin2024cloud}.

\subsection{Algorithm Design for CED Task Scheduling}
\label{subsec22}

\textbf{Mathematical programming and rule-based methods.}
Integer programming methods~\cite{wang2022integer} and constructive heuristics (e.g., First-Come-First-Served, Min-Min, Earliest-Deadline-First~\cite{naik2025energy}) provide baselines but cannot scale to large instances or adapt to heterogeneous task features.

\textbf{Hyper-heuristic and adaptive methods.}
Hyper-heuristics~\cite{xiao2019cooperative,burke2013hyper} select low-level heuristics at a higher abstraction level. Bandit-based adaptive operator selection (AOS) methods~\cite{sun2020adaptive,de2021comparative,dacosta2008adaptive,karafotias2014parameter} dynamically select operators based on performance feedback. Laili et al.~\cite{laili2023dsac} propose DSAC-DE, which uses a discretized soft actor--critic to configure differential evolution for CED scheduling. However, these methods typically operate at a global level without distinguishing between different decision subspaces. Island models~\cite{gong2011distributed,da2023behavior,whitley1999island} maintain diversity through spatial partitioning but have not been combined with structure-aware decomposition for CED scheduling.

\textbf{Deep reinforcement learning (DRL) methods.}
DRL methods~\cite{gu2025deep,mangalampalli2024efficient,zheng2022deep} formulate scheduling as a Markov decision process (MDP) and learn policies through training episodes. While DRL can adapt to dynamic contexts, it requires extensive offline training time and exhibits limited generalization across problem instances, especially in high-dimensional discrete action spaces typical of CED scheduling.

\section{Problem Formulation}
\label{sec3}

\subsection{System Architecture}
\label{subsec31}

The CED system comprises three tiers. The \emph{cloud tier} $\mathcal{C}=\{c_0,\ldots,c_{N_c-1}\}$ provides high computation capacity with communication latency. The \emph{edge tier} $\mathcal{E}=\{e_0,\ldots,e_{N_e-1}\}$ balances computation speed and proximity. The \emph{device tier} $\mathcal{D}=\{d_0,\ldots,d_{N_d-1}\}$ executes shop-floor operations with minimal communication latency but limited computation capacity.

The system handles two workload categories. CE tasks $\mathcal{T}_{CE}=\{T^{CE}_1,\ldots,T^{CE}_{N_{CE}}\}$ are offloaded to the cloud or edge tier. Each CE task $T^{CE}_i$ has computation workload $comp_i$, communication size $comm_i$, precedence set $P_i$, interactive dependency set $\mathcal{L}_i$, and available edge server list $A_i^{E} \subseteq \mathcal{E}$. Manufacturing jobs $\mathcal{J}=\{j_1,\ldots,j_{N_j}\}$ each consist of a sequence of operations $\mathcal{O}_j=\{o_{j,1},\ldots,o_{j,n_j}\}$, where each operation $o_{j,k}$ has processing time $p_{j,k}$ and eligible device set $D_{j,k} \subseteq \mathcal{D}$.

\subsection{Decision Variables}
\label{subsec32}

Let $N_{\mathrm{ops}}=\sum_{j=1}^{N_j} n_j$. A candidate solution is encoded as a continuous vector $\mathbf{x} \in [0,1]^D$ where $D = 2N_{CE} + 2N_{\mathrm{ops}}$:
$$
\mathbf{x} = \big[
\underbrace{x_1, \ldots, x_{N_{CE}}}_{\text{tier selection}},\;
\underbrace{r_1, \ldots, r_{N_{CE}}}_{\text{server selection}},\;
\underbrace{\pi_1, \ldots, \pi_{N_{\mathrm{ops}}}}_{\text{sequencing}},\;
\underbrace{m_1, \ldots, m_{N_{\mathrm{ops}}}}_{\text{device assignment}}
\big].
$$

The continuous values are decoded into discrete decisions as follows.

\textbf{Tier selection.} For CE task $T^{CE}_i$: if $x_i < 0.5$, assign to cloud; otherwise assign to edge.

\textbf{Server selection.} For CE task $T^{CE}_i$ with variable $r_i \in [0,1]$: if assigned to cloud, select server $c_{\lfloor r_i \cdot (N_c-1)\rfloor}$; if assigned to edge, select server $\mathcal{A}_i^E[\lfloor r_i \cdot (|\mathcal{A}_i^E|-1)\rfloor]$.

\textbf{Operation sequencing.} The priority vector $\boldsymbol{\pi}$ determines execution order by sorting operations in ascending order of their priority values: $\text{ExecutionOrder} = \operatorname{argsort}(\pi_1,\ldots,\pi_{N_{\mathrm{ops}}})$.

\textbf{Device assignment.} Let $\text{ExecutionOrder} = [op_0, \ldots, op_{N_{\mathrm{ops}}-1}]$. The device gene is indexed by the rank $i$ in the execution order. For the $i$-th scheduled operation $op_i$ with eligible device set $D(op_i)$:
$\text{Device}(op_i) = D(op_i)[\lfloor m_i \cdot (|D(op_i)|-1)\rfloor]$.
Because the device gene's meaning depends on the sequencing-induced execution order, the device block is coupled with the sequencing block in the cooperative coevolution scheme.

\subsection{Constraints}
\label{subsec33}

\textbf{CE precedence.} $ST_i^{CE} \geq ET_k^{CE}$ for all $T_k^{CE} \in P_i$.

\textbf{Operation sequence.} Within each job: $ST_{j,k+1} \geq ET_{j,k}$ for $k=1,\ldots,n_j-1$.

\textbf{Device capacity.} Operations on the same device cannot overlap:
if $\text{Device}(o_{j,k}) = \text{Device}(o_{j',k'})$, then $ST_{j,k} \geq ET_{j',k'}$ or $ST_{j',k'} \geq ET_{j,k}$.

\textbf{Data dependency.} For CE tasks with data exchange: $ET_i^{CE} + T^{CE}_{comm}(i,k) \leq ST_k^{CE}$ for all $T_k^{CE} \in \mathcal{L}_i$.

\textbf{CE execution model.} CE tasks on the same server are not scheduled through an explicit queue. Their completion times are approximated from dependency release times, communication delays, and load-dependent penalties. Device availability constraints are ensured by the decoding rules; temporal constraints are verified by discrete-event simulation during fitness evaluation.

\subsection{Objectives}
\label{subsec34}

The CE-layer completion time and total energy consumption are defined as:
\begin{align}
f_1(\mathbf{x}) &= \max_{i \in \{1,\ldots,N_{CE}\}} ET_i^{CE}, \label{eq:f1} \\
f_2(\mathbf{x}) &= QN \cdot \sum_{i=1}^{N_{CE}} t_i^{\mathrm{comm}}
+ \sum_{c \in \mathcal{C}} \mathrm{EnergyList}[u_c] \cdot \frac{T_c^{act}}{1000} \nonumber \\
&\quad + \sum_{e \in \mathcal{E}} \mathrm{EnergyList}[u_e] \cdot \frac{T_e^{act}}{1000}, \label{eq:f2}
\end{align}
where $t_i^{\mathrm{comm}}$ is the communication time, $QN$ is a communication power coefficient, $u_c, u_e$ are discretized utilization indices, $\mathrm{EnergyList}[\cdot]$ is a power lookup table, and $T_s^{act}$ is the active time of server $s$.

The two objectives are combined via weighted aggregation:
\begin{equation}
f(\mathbf{x}) = \alpha \cdot \frac{f_1(\mathbf{x})}{f_1^{ref}} + (1-\alpha) \cdot \frac{f_2(\mathbf{x})}{f_2^{ref}}, \quad \alpha \in (0,1)
\label{eq:scalar}
\end{equation}
where $f_1^{ref}$ and $f_2^{ref}$ are reference values computed once per instance from a shared baseline initializer, kept constant across all algorithms and runs for fair comparison. Unless otherwise stated, $\alpha = 0.5$.


\section{The Proposed CCHIHH Algorithm}
\label{sec4}

This section presents the CCHIHH algorithm. Section~\ref{subsec41} introduces cooperative coevolution as the problem decomposition foundation. Sections~\ref{subsec42}--\ref{subsec44} describe the three main contributions: the contextual bandit for operator selection, the heterogeneous island model with ring migration, and the stability-gating mechanism. Section~\ref{subsec45} describes the lower-layer operator pools. Section~\ref{subsec46} presents the overall workflow and pseudocode. Section~\ref{subsec47} analyzes the time complexity.

\subsection{Cooperative Coevolution for Problem Decomposition}
\label{subsec41}

As discussed in Section~\ref{sec1}, applying operators globally to the entire decision vector mixes improvement signals from fundamentally different decision types. To address this, CCHIHH decomposes the solution vector into three blocks:
\begin{itemize}
    \item \textbf{Offload block} $\mathbf{x}_{\text{off}} \in [0,1]^{2N_{CE}}$: tier selection and server assignment for CE tasks.
    \item \textbf{Sequence block} $\mathbf{x}_{\text{seq}} \in [0,1]^{N_{\mathrm{ops}}}$: priority values determining operation execution order.
    \item \textbf{Device block} $\mathbf{x}_{\text{dev}} \in [0,1]^{N_{\mathrm{ops}}}$: rank-conditioned device assignment for each operation.
\end{itemize}

In each generation, the three blocks are optimized sequentially using cooperative coevolution~\cite{omidvar2013cooperative,ma2018survey}. When one block is being optimized, the other two blocks are held fixed at their current best values (context vectors). After each block completes its optimization step, the context vectors are updated. This sequential update allows each block to respond to changes made by the other blocks within the same generation.

Note that the device block is coupled with the sequence block: the semantic meaning of each device gene depends on the execution order induced by the sequence block (Section~\ref{subsec32}). The cooperative coevolution scheme naturally handles this coupling by always evaluating the full solution (all three blocks concatenated) during fitness computation.

\subsection{Contextual Bandit for Operator Selection}
\label{subsec42}

Each block requires different operators suited to its search landscape. Rather than fixing an operator schedule, CCHIHH uses a linear contextual bandit to select operators online based on the current search state. Each block on each island maintains its own bandit instance, so operator preferences can differ both across blocks and across islands.

\textbf{Search state.}
A seven-dimensional state vector $\mathbf{s} = [s_1, \ldots, s_7]^T$ is computed from the current island population to characterize the search status:
\begin{itemize}
    \item $s_1$ (generation progress): $s_1 = g / G_{\max}$, where $g$ is the current generation and $G_{\max}$ is the maximum number of generations.
    \item $s_2$ (stagnation level): $s_2 = \min(1, \tau_{\text{stag}} / (0.25 G_{\max} + 1))$, where $\tau_{\text{stag}}$ counts the number of consecutive generations without improvement.
    \item $s_3$ (recent improvement): the average relative improvement over the last $k$ generations, $\bar{I}_k = \frac{1}{k}\sum_{i=1}^k \frac{f_{\text{old}} - f_{\text{new}}}{|f_{\text{old}}|}$, clipped to $[0,1]$.
    \item $s_4$ (population diversity): $s_4 = \mathcal{D}_{pop} / (\mathcal{D}_{pop} + 1)$, where $\mathcal{D}_{pop}$ is the average variance across dimensions.
    \item $s_5$ (operator success rate): fraction of the last $k$ generations where the selected operator produced an improvement.
    \item $s_6$ (last reward): $s_6 = 0.5 + 0.5 \tanh(r_{\text{last}})$, bounding the most recent reward to $[0,1]$.
    \item $s_7$ (bias): constant $1.0$, enabling the model to learn baseline operator preferences.
\end{itemize}

\textbf{Operator scoring and selection.}
Each operator $op$ has a weight vector $\mathbf{w}_{op} \in \mathbb{R}^7$. The estimated value of selecting operator $op$ in state $\mathbf{s}$ is:
\begin{equation}
\text{score}(op, \mathbf{s}) = \mathbf{w}_{op}^T \mathbf{s}.
\label{eq:bandit_score}
\end{equation}
Operators are selected using an $\epsilon$-greedy rule: with probability $\epsilon(g)$, a random operator is chosen; otherwise, the operator with the highest score is selected. The exploration rate decays as:
\begin{equation}
\epsilon(g) = \max\!\left(\epsilon_{\min},\; \epsilon_0 \cdot \exp\!\left(-\epsilon_k \cdot \frac{g}{G_{\max}}\right)\right).
\label{eq:epsilon}
\end{equation}

\textbf{Reward and weight update.}
After applying the selected operator, the reward is computed as:
\begin{equation}
r = \mathrm{clip}(I + \lambda \cdot \Delta D,\; -c,\; c),
\label{eq:reward}
\end{equation}
where $I$ is the fitness improvement ratio, $\Delta D$ is the change in population diversity, $\lambda$ balances the two terms, and $c$ is a clipping constant. The operator weight vector is updated by:
\begin{equation}
\mathbf{w}_{op} \leftarrow \mathbf{w}_{op} + \eta_t (r - \mathbf{w}_{op}^T \mathbf{s})\, \mathbf{s},
\label{eq:weight_update}
\end{equation}
where the learning rate decays as $\eta_t = \eta_0 \exp(-\eta_k \, t)$, and $t$ counts the number of updates for this specific operator. This per-operator counter ensures that frequently selected operators decay faster, maintaining sensitivity for less-used operators.

The pseudocode for the contextual bandit is given in Algorithm~\ref{alg:contextual_bandit_hh}. The algorithm takes the island population, generation counter, and stagnation counter as inputs. Steps~1--9 compute the state vector from population statistics. Steps~10--15 select an operator via the $\epsilon$-greedy rule. Steps~16--19 apply the operator and update the population. Steps~20--24 compute the reward and update the operator weights.

\begin{algorithm}[H]
\caption{Contextual Bandit Operator Selection (per block, per island)}
\label{alg:contextual_bandit_hh}
\begin{algorithmic}[1]
\REQUIRE island population $P_{isl}$, generation $g$, stagnation counter $\tau_{\mathrm{stag}}$, last reward $r_{\mathrm{last}}$
\ENSURE updated $P_{isl}$ and operator weights $\mathbf{W}$

\STATE Compute state vector $\mathbf{s} = [s_1, \ldots, s_7]^T$ from $P_{isl}$, $g$, $\tau_{\mathrm{stag}}$, $r_{\mathrm{last}}$
\STATE Compute $\epsilon(g)$ by Eq.~(\ref{eq:epsilon})

\IF{$\mathrm{rand}() < \epsilon$}
  \STATE $op \gets \mathrm{RandomChoice}(\mathcal{O}_{\text{block}})$
\ELSE
  \STATE $op \gets \arg\max_{i \in \mathcal{O}_{\text{block}}} \mathbf{w}_i^T \mathbf{s}$
\ENDIF

\STATE Record $f_{\mathrm{old}} \gets \mathrm{BestFitness}(P_{isl})$, $D_{\mathrm{old}} \gets \mathrm{Diversity}(P_{isl})$
\STATE $P'_{isl} \gets \mathrm{ApplyOperator}(op, P_{isl})$
\STATE $P_{isl} \gets \mathrm{SelectionUpdate}(P_{isl}, P'_{isl})$
\STATE Record $f_{\mathrm{new}} \gets \mathrm{BestFitness}(P_{isl})$, $D_{\mathrm{new}} \gets \mathrm{Diversity}(P_{isl})$

\STATE $I \gets (f_{\mathrm{old}} - f_{\mathrm{new}}) / (|f_{\mathrm{old}}| + 10^{-9})$
\STATE $r \gets \mathrm{clip}(I + \lambda (D_{\mathrm{new}} - D_{\mathrm{old}}),\; -c,\; c)$
\STATE $\eta_t \gets \eta_0 \exp(-\eta_k \, t)$
\STATE $\mathbf{w}_{op} \gets \mathbf{w}_{op} + \eta_t (r - \mathbf{w}_{op}^T \mathbf{s})\, \mathbf{s}$

\RETURN $P_{isl}, \mathbf{W}$
\end{algorithmic}
\end{algorithm}

\subsection{Heterogeneous Islands with Ring Migration}
\label{subsec43}

A single population evolving with one set of bandit weights can converge to a single search strategy. To maintain multiple complementary strategies, CCHIHH partitions the total population of size $N$ into $M$ islands, each of size $N/M$. Each island maintains its own bandit weights for every block, so different islands can develop different operator preferences.

\textbf{Ring migration.}
Every $T_{\text{mig}}$ generations, the best individual from each island is copied to the next island in a ring topology. The worst individual on the receiving island is replaced. This bidirectional ring migration enables information propagation: a good solution discovered on one island can gradually spread to all islands, but the slow propagation speed prevents immediate homogenization.

The migration mechanism is lightweight: its per-event cost is $\mathcal{O}(M \cdot D_{\text{block}})$, and amortized over $T_{\text{mig}}$ generations, it is dominated by the fitness evaluation cost.

\subsection{Stability-Gated Diversity Control}
\label{subsec44}

Each block's operator pool includes a \emph{Block Resample} operator that re-initializes a fraction of dimensions to random values, providing a strong escape mechanism from local optima. However, applying this operator during productive convergence phases can disrupt promising solutions. This tension is especially acute on large instances where the landscape contains many local optima.

The gating mechanism resolves this tension with a simple rule. When the bandit selects a Block Resample operator, the mechanism checks the stagnation counter $\tau_{\text{stag}}$:
\begin{equation}
op_{\text{exec}} = \begin{cases}
op_{\text{bandit}}, & \text{if } op_{\text{bandit}} \notin \mathcal{O}_{\text{resample}}, \\
op_{\text{bandit}}, & \text{if } op_{\text{bandit}} \in \mathcal{O}_{\text{resample}} \wedge \tau_{\text{stag}} \geq T_{\text{gate}}, \\
op_{\text{fallback}}, & \text{if } op_{\text{bandit}} \in \mathcal{O}_{\text{resample}} \wedge \tau_{\text{stag}} < T_{\text{gate}},
\end{cases}
\label{eq:gating}
\end{equation}
where $T_{\text{gate}}$ is the stagnation threshold, and $op_{\text{fallback}}$ is a fixed fallback operator for each block (DE for offload, SWAP for sequence, GDE for device). The stagnation counter resets to zero whenever the best fitness improves by more than $10^{-12}$, and increments by one otherwise.

In other words, Block Resample is only allowed when the search has stagnated for at least $T_{\text{gate}}$ consecutive generations. During productive phases, the bandit's Resample selection is replaced by a safe exploitation operator. This ensures that diversity injection is delayed until there is evidence that the current search trajectory has exhausted its potential.

The complete gating logic is given in Algorithm~\ref{alg:gating_mechanism}. Steps~1--8 perform operator selection via the contextual bandit. Steps~9--14 apply the gating rule. Steps~15--18 apply the operator and update the population. Steps~19--22 update the stagnation counter.

\begin{algorithm}[H]
\caption{Gating Mechanism for Operator Selection}
\label{alg:gating_mechanism}
\begin{algorithmic}[1]
\REQUIRE $P_{isl}$, generation $g$, block ID, $\tau_{\text{stag}}$, $T_{\text{gate}}$
\ENSURE executed operator $op_{\text{exec}}$, updated $P_{isl}$, updated $\tau_{\text{stag}}$

\STATE Compute state $\mathbf{s}$ and select $op_{\text{bandit}}$ via Algorithm~\ref{alg:contextual_bandit_hh}

\STATE Set fallback: DE (offload), SWAP (sequence), GDE (device)

\IF{$op_{\text{bandit}} \in \mathcal{O}_{\text{resample}}$ \textbf{and} $\tau_{\text{stag}} < T_{\text{gate}}$}
    \STATE $op_{\text{exec}} \gets op_{\text{fallback}}$
\ELSE
    \STATE $op_{\text{exec}} \gets op_{\text{bandit}}$
\ENDIF

\STATE $f_{\text{old}} \gets \mathrm{BestFitness}(P_{isl})$
\STATE $P_{isl} \gets \mathrm{ApplyAndSelect}(op_{\text{exec}}, P_{isl})$
\STATE $f_{\text{new}} \gets \mathrm{BestFitness}(P_{isl})$

\IF{$f_{\text{new}} < f_{\text{old}} - 10^{-12}$}
    \STATE $\tau_{\text{stag}} \gets 0$
\ELSE
    \STATE $\tau_{\text{stag}} \gets \tau_{\text{stag}} + 1$
\ENDIF

\RETURN $op_{\text{exec}}, P_{isl}, \tau_{\text{stag}}$
\end{algorithmic}
\end{algorithm}

\subsection{Lower-Layer Operators}
\label{subsec45}

Each block is equipped with a pool of four operators tailored to its search landscape, as summarized in Table~\ref{tab:operator_pool}.

\begin{table}[H]
    \centering
    \small
    \caption{Operator pool for each block.}
    \label{tab:operator_pool}
    \begin{tabular}{ll}
        \toprule
        \textbf{Block} & \textbf{Operators} \\
        \midrule
        Offload  & GA, DE, BitFlip, Block Resample \\
        Sequence & GA, Sequence Swap, VNS, Block Resample \\
        Device   & DE, Gbest-DE (GDE), L\'{e}vy Flight, Block Resample \\
        \bottomrule
    \end{tabular}
\end{table}

The offload block handles coupled discrete decisions (cloud vs.\ edge, server ID). It includes a Genetic Algorithm with simulated binary crossover (SBX)~\cite{deb1995simulated} and polynomial mutation for controlled offspring distribution, a DE/current-to-\textit{p}best/1 operator~\cite{zhang2009jade} that guides the mutation toward elite individuals while maintaining diversity through an external archive of replaced solutions, a BitFlip operator that toggles the tier decision (mapping $x_i < 0.5$ to 0.75 and $x_i \geq 0.5$ to 0.25) while applying Cauchy-distributed perturbations~\cite{choi2021improved} to the server-selection subvector, and an Opposition-Based Learning (OBL) Resample operator~\cite{tizhoosh2005opposition}.

The sequence block optimizes real-valued priority vectors that determine operation execution order. SBX-based GA preserves partial ordering through its parent-similarity property. Segment Shift performs Or-opt-style moves~\cite{or1976traveling} by extracting a short contiguous sub-segment of length 1--3 and reinserting it at a random position, providing more structured perturbations than pairwise swaps. Heterogeneous Variable Neighborhood Search (VNS)~\cite{hansen2001variable} performs local search around elite individuals using five distinct neighborhood structures of increasing perturbation strength: single swap, adjacent swap, segment reversal, segment shift, and sub-segment scramble. OBL Resample provides escape capability.

The device block assigns operations to devices via continuous values mapped through bucket decoding. DE/current-to-\textit{p}best/1 with archive exploits correlations across device assignments while benefiting from elite guidance and archived diversity. Rank-based Selective Pressure DE (RSP-DE)~\cite{stanovov2018lshade} employs the current-to-\textit{p}best/1 mutation with tournament-based donor selection, where $\mathbf{x}_{r_1}$ is chosen via binary tournament to bias the difference vector toward higher-quality regions. Cauchy Walk perturbs a fraction of dimensions with Cauchy-distributed steps ($\gamma=1$), whose heavier tails compared to the standard L\'{e}vy distribution ($\beta=1.5$) enable more frequent long-range jumps for escaping local optima. OBL Resample provides large-scale re-initialization.

For all blocks, OBL Resample selects $\lceil 0.2 \cdot D_{\text{block}} \rceil$ dimensions uniformly at random with replacement. For each selected dimension, the operator applies the opposite-point transformation $x_i' = 1 - x_i$ with probability 0.5; otherwise, it re-initializes the dimension to $\mathcal{U}(0,1)$. This hybrid strategy exploits the symmetry of the search space while preserving random exploration capability. All operators use fixed parameters to ensure stationary behavior, enabling the contextual bandit to learn stable operator--outcome mappings. Detailed operator parameters (e.g., SBX distribution index $\eta_c$, DE scale factor $F$, crossover rate $CR$, top-$p$ fraction, VNS neighborhood levels) are specified in Section~\ref{subsec51}.

\subsection{Overall Workflow}
\label{subsec46}

\begin{figure}[t]
    \centering
    \includegraphics[width=\linewidth]{WorkFlow.png}
    \caption{Overall workflow of CCHIHH. The population is partitioned into $M$ islands. In each generation, the three blocks are optimized sequentially via cooperative coevolution. Within each block, the contextual bandit selects operators (subject to the gating mechanism), and ring migration periodically transfers the best individuals between neighboring islands.}
    \label{fig:cchihh_framework}
\end{figure}

The overall workflow of CCHIHH is illustrated in Fig.~\ref{fig:cchihh_framework}. The algorithm proceeds as follows:

\begin{enumerate}
    \item \textbf{Initialization}: Generate a population of $N$ individuals and partition them into $M$ islands. Initialize bandit weights to zero for all operators on all blocks and islands.
    \item \textbf{Main loop} (for $G_{\max}$ generations):
    \begin{enumerate}
        \item For each block (offload, sequence, device) in sequence:
        \begin{enumerate}
            \item For each island in parallel: select an operator via the contextual bandit with gating (Algorithm~\ref{alg:gating_mechanism}), apply it to the island population, and update bandit weights.
            \item Update the context vector for the next block.
        \end{enumerate}
        \item Every $T_{\text{mig}}$ generations: perform ring migration across all islands.
    \end{enumerate}
    \item \textbf{Output}: Return the best solution found across all islands.
\end{enumerate}

\subsection{Time Complexity}
\label{subsec47}

Let $N$ be the population size, $M$ the number of islands, $G$ the maximum generations, and $N_{\mathrm{ops}}$ the total number of operations. A single fitness evaluation requires $\mathcal{O}(N_{\mathrm{ops}} \log N_{\mathrm{ops}} + N_{\mathrm{ops}} \bar{d})$ for sorting and discrete-event simulation, where $\bar{d}$ is the average number of eligible devices per operation.

Across $K=3$ blocks and $M$ islands, the per-generation cost is dominated by fitness evaluations: $\mathcal{O}(K \cdot N \cdot N_{\mathrm{ops}} \log N_{\mathrm{ops}})$. The bandit overhead is $\mathcal{O}(K \cdot N)$ per generation, and migration costs $\mathcal{O}(M \cdot D_{\text{block}})$ every $T_{\text{mig}}$ generations---both negligible compared to fitness evaluation.

The overall complexity is therefore:
\begin{equation}
T_{\text{total}} = \mathcal{O}(G \cdot N \cdot N_{\mathrm{ops}} \log N_{\mathrm{ops}}),
\end{equation}
which is the same asymptotic order as single-population baselines (GA, DE) per generation, though CCHIHH evaluates $K \times N$ solutions per generation due to the three-block structure. The island framework is naturally suitable for parallel execution across $M$ islands.

Implementation optimizations include reusable workspace buffers to avoid repeated memory allocation, pre-allocated sorting arrays, and $\mathcal{O}(1)$ timestamp-based duplication checks.


\section{Experiments and Discussions}
\label{sec5}

\subsection{Experimental Settings}
\label{subsec51}

\textbf{Problem instances.}
Three scales of problem instances are used:
\begin{itemize}
    \item \textbf{T100}: 100 CE tasks, 100 cloud servers, 100 edge servers, 300 devices.
    \item \textbf{T200}: 200 CE tasks, 100 cloud servers, 100 edge servers, 300 devices.
    \item \textbf{T500}: 500 CE tasks, 200 cloud servers, 200 edge servers, 800 devices.
\end{itemize}

\textbf{Algorithm parameters.}
Population size $N = 40$, number of islands $M = 8$ (subpopulation size 5), maximum generations $G_{\max} = 10{,}000$, migration interval $T_{\text{mig}} = 5$ generations. Bandit parameters: initial exploration rate $\epsilon_0 = 0.2$, minimum $\epsilon_{\min} = 0.02$, decay rate $\epsilon_k = 0.01$; learning rate $\eta_0 = 0.05$, decay $\eta_k = 0.002$; reward clipping $c = 0.2$; diversity weight $\lambda = 0.1$. Gating threshold $T_{\text{gate}} = 15$ generations. Operator parameters: DE scale factor $F = 0.5$, crossover rate $CR = 0.5$; GDE uses randomized $F \sim \mathcal{U}(0.2, 0.8)$ and $CR \sim \mathcal{U}(0.1, 0.6)$ per island per generation; BitFlip probability $p_{\text{flip}} = 0.1$; VNS neighborhood levels $k_{\max} = 5$ with $n_s = 5$ candidates per level; L\'{e}vy flight perturbation fraction $p_d = 0.1$, stability parameter $\beta = 1.5$, step coefficient $\alpha_{\text{levy}} = 0.01$; Block Resample rate $\rho = 0.2$; GA mutation probability $p_m$ per individual with single-dimension reset.

\textbf{Baseline algorithms.}
\begin{itemize}
    \item \textbf{GA}: Genetic algorithm with blend crossover and Gaussian mutation.
    \item \textbf{DE}: Standard differential evolution with $F = 0.5$, $CR = 0.5$.
    \item \textbf{Gbest-DE}: DE variant incorporating the global best individual.
    \item \textbf{CGA}~\cite{wang2020task}: GA with catastrophe strategy for cloud--edge scheduling.
    \item \textbf{IMOMA}~\cite{cui2025efficient}: Memetic algorithm with opposition-based learning and dual local search.
    \item \textbf{PPO}~\cite{zheng2022deep}: Proximal Policy Optimization trained independently per seed; results summarize 10 independently trained policies.
    \item \textbf{DSAC-DE}~\cite{laili2023dsac}: Discretized soft actor--critic configured DE, re-implemented following the original hyperparameters with the same evaluation engine as all other methods.
\end{itemize}

\textbf{Ablation variants} (for Section~\ref{subsec52}):
CCHIHH-full (all components), CCHIHH-noCC (without cooperative coevolution), CCHIHH-noHI (single population, no islands), CCHIHH-noCB (fixed operators, no bandit), CCHIHH-noMig (no migration), CCHIHH-noGate (no gating).

\textbf{Fairness and reproducibility.}
All algorithms share the same solution encoding/decoding and discrete-event simulation engine. Each method runs for 10{,}000 generations with 10 random seeds (1--10). Normalization references $f_1^{ref}$ and $f_2^{ref}$ are computed once per instance using a shared initializer. CCHIHH evaluates $K \times N$ solutions per generation due to the three-block structure; comparisons are iteration-matched rather than evaluation-matched. Wall-clock runtime is additionally reported. Statistical tests use the two-sided Wilcoxon signed-rank test ($\alpha = 0.05$).

\textbf{Platform.}
Intel Ultra-7 255HX (24 cores), 32~GB RAM, Windows~11. All algorithms are implemented in C++ with CMake O2 optimization.

\section{Conclusion}
\label{sec6}

This paper addressed the cloud--edge--device (CED) collaborative scheduling problem arising in distributed manufacturing, where heterogeneous decision subspaces---offloading, sequencing, and rank-conditioned device assignment---are coupled through synchronization constraints. The central finding is that \emph{when CED scheduling is composed of structurally distinct yet coupled decision subspaces, search control must also be structured, localized, and stage-aware}. The proposed CCHIHH framework operationalizes this principle through four layers---structure-aware cooperative coevolution, localized contextual bandit adaptation, parallel heterogeneous island exploration, and stability-gated regime switching---forming a unified architecture whose value amplifies with industrial scale.

Extensive experiments on benchmark instances with up to 500 tasks and 800 devices demonstrate that CCHIHH achieves 33.59\% and 43.99\% improvement over CGA and IMOMA on T500, with statistically significant results confirmed by both Wilcoxon signed-rank and Friedman tests ($p < 0.05$). Ablation studies reveal a consistent scale-dependent contribution pattern: all framework layers become increasingly beneficial as problem complexity grows, while the gating mechanism serves as a scale-specific safeguard effective primarily on large-scale instances. Across all scales, CCHIHH maintains bounded run-to-run dispersion (CV~$\le$~0.051).

\textbf{Industrial Applicability.}
The proposed framework is designed with practical manufacturing deployment in mind. In a representative automotive body-in-white production scenario, CCHIHH can serve as the optimization engine within a Manufacturing Execution System (MES): given a batch of CE tasks (structural computation, digital twin updates, quality inspection analytics) and a set of manufacturing operations (welding, painting, assembly) with their device eligibility and synchronization constraints, CCHIHH generates an optimized three-tier schedule within minutes on commodity hardware. The Gantt chart output (Figure~\ref{fig:gantt_T200}) is directly interpretable by production planners and can be fed into real-time dispatchers. The bounded run-to-run variability (CV~$\le$~0.051) ensures that repeated invocations under identical conditions produce consistent schedules, a critical requirement for production reliability. Furthermore, the sub-five-minute runtime on industrial-scale instances (500 tasks, 800 devices) is compatible with shift-level or batch-level re-scheduling cycles typical in discrete manufacturing.

\textbf{Limitations.}
The current evaluation uses self-generated benchmark instances rather than community-standard test sets or data from real production lines. Although DSAC-DE is re-implemented following the original hyperparameters, minor implementation-level differences (e.g., neural network library, floating-point behavior) may still exist relative to the original codebase. The single-objective weighted aggregation relies on a scalar reward signal; extending the framework to explicit Pareto optimization would require redesigning the bandit's reward structure (e.g., using hypervolume contribution), which constitutes a non-trivial architectural modification. The population size ($N=40$, with 5 individuals per island) is relatively small by evolutionary computation standards, and population-size sensitivity warrants further investigation.

\textbf{Future Work.}
Future research directions include (i)~validation on real-world manufacturing datasets from automotive and electronics production lines, (ii)~principled decomposition strategies that generalize beyond the current three-block design to accommodate varying manufacturing process structures, (iii)~multi-objective optimization with Pareto-front analysis using redesigned reward structures, and (iv)~online scheduling scenarios where tasks arrive continuously, supported by distributed and GPU-accelerated implementations. Code and benchmark data will be made publicly available upon acceptance.
